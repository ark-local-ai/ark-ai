# 5 · 企业级演进路线（Agent 架构详解）

> 从「本地单机原型」演进到「企业级多用户」的分阶段路线。每阶段说清：动机、改什么、风险。当前已跑通**阶段 0~2 主体**，正处于**可靠性加固（M24~M27）**。

---

## 阶段 0 · 单机全栈闭环（✅ 已通）
- **现状**：React 前端 + Fastify 后端 + 单机 SQLite；任务 mock 编排 + md 文件交付；SSE 实时进度。
- **价值**：验证「一句话 → 拆步骤 → 执行 → 交付可编辑文件」的核心主张，全链路跑通。
- **局限**：编排是假计划、无真实 LLM、只产 md、数据单机、用户单账号。

---

## 阶段 1 · 接真实智能（价值跃迁，主体已完成）
**动机**：让"拆步骤/执行/验收"由真模型驱动，而非硬编码。

- [x] **接 LLM**：openai 兼容 adapter（DeepSeek/OpenAI/Ollama 通吃），`planner.llmPlan` 拆真步骤（M9），无 key 降级脚本计划器。
- [x] **工具执行**：`tools/registry.ts` 工具注册表 + `tools/office.ts` 用 pptxgenjs/exceljs/docx 生成可编辑 Office 文件（M10 + M4），多 Agent 内容管线（M10b pipeline 分析/写手/校验）。
- [x] **模型渠道管理**：DB 持久化渠道 CRUD + 验活 + 路由（B1）；M14 起 `chatWithFailover` 多渠道逐个尝试、M15 成本/延迟/优先级加权、M27 每渠道熔断。
- **风险**：LLM 输出不可控 → 已做自检验收 + 失败重试（verifier + M16 失败兜底 + M17 重试）。
- **架构影响**：局部扩展于 orchestrator/router，不影响 API 形状。

---

## 阶段 2 · 多用户 / 鉴权 / 数据分离（主体已完成）
**动机**：从"一个本机工作台"变成"团队可用"。**门禁强度用户已拍板 = 软门禁**（有账号体系、不强制登录，保 local-first）。

- [x] 账号体系（DB session）+ 用户 → 任务/空间/对话归属（M12 登录、M13 多用户隔离）
- [x] 多工作空间隔离（M11 spaces 表 + 每个项目独立空间与交付目录）
- [x] 数据表加 `user_id`；资源按「自己的 + 全局」过滤（M13）
- [ ] （可选，用户拍板不做硬门禁）业务路由强制 401 —— 当前软门禁，未登录可自由用本地
- **架构影响**：DB schema、鉴权（routes/auth.ts + currentUser）、存储路径管理（活动空间）。

---

## 阶段 3 · 分布式 / 高可用（部分已提前落地可靠性）
**动机**：多实例、任务量大、不丢事件。

- [ ] SQLite → **PostgreSQL**（`node:sqlite` 是单机；分布需真库 + 连接池）
- [ ] 事件总线内存 Map → **Redis pub/sub** 或消息队列（多实例共享进度广播）——M21 已在单机内做全局 SSE，分布化仍待 Redis
- [x] **任务编排可重试/可恢复**（M17 重试/删除；M24 进程重启后从 DB 重建未完成 queue/running 任务续跑）
- [x] **队列化任务**（M16 runner.ts 串行队列 + 失败兜底，替代真正并发；后续如需并发上 p-limit）
- **风险**：基础设施复杂度上升，与"本地优先"拧巴 → 应做「可剥离」设计：本地仍是单机 SQLite，企业部署才上 PG。

## 阶段 4 · 桌面 + IM 触达（回到产品主张）
**动机**：产品定位是「本地优先 + 数据不出机 + 随时派活」。

- [ ] **Tauri 2 桌面壳**（复用前端；Rust 后端可访问本地文件）——M8 已建项目但未打包，交给小伙伴
- [ ] **IM 桥**（企业微信/飞书/QQ）：外出发消息指挥本机干活，干完推回文件——文档里的"远程派活"落点
- [ ] 记忆 / 内置浏览器（真渲染+表单填写）
- **架构影响**：新增 IM 网关层；桌面用 Tauri 命令替代/并行 HTTP。

## 可靠性加固（M24~M32，当前所在）
不属于单一阶段的横向加固，对应文档路线图 Stage 1「可靠性」：
- **M25 自动化测试**：vitest（ARK_DB_PATH/ARK_TEST 隔离临时库）store/events/runner/HTTP 57 用例；`npm test`/`typecheck(tsconfig.test.json)`/`build` 三件套全绿（测试揪出 2 个潜伏 bug）。
- **M26 结构化日志**：util/log.ts pino（service 常驻 + taskId 贯穿），任务全生命周期可追踪、可按 reqId 串联 HTTP。
- **M27 多渠道熔断**：连续失败 5 次 open + 10s cooldown + half-open 探测，避免反复重试已知坏源。
- **M24 进程重启恢复**：启动时重建未完成任务续跑。
- **M28 验收回归评测集**：`test/acceptance.test.ts` 把「交付可编辑 Office」核心卖点固化为 12 个回归断言（PPT/Excel/Word 真实生成 + 合法 + ExcelJS 读回），共 43 用例；任何改动让某类交付退化即变红。配置「验收回归评测集：把历史成功任务固化为评测集」的价值落点。
- **M29 操作审计日志**：根 onResponse 钩子统一审计所有写请求（POST/PUT/DELETE→/api/*），当前用户/匿名、method+url→可读中文动作+目标 id；`GET /api/audit` 可查；一处实现覆盖全部端点、零侵入路由。对应「审计日志」类治理能力。
- **M30 任务并发控制**：runner 把 M16 的严格串行 `tail` 链改为**信号量受控并发**——默认同跑 2 个（可 `ARK_MAX_CONCURRENCY` 覆盖）、FIFO 排队、`getQueueStats`/`GET /api/queue` 暴露 active/queued/concurrency，统计页加实时队列卡。对应 Stage 2「任务并发控制：信号量限制并行任务数，避免 CPU/LLM 打满」的点名落地。
- **M31 逐步断点续跑**：进程重启不再从头重跑——每个步骤都在置 done 时把产出整篇持久化进 `steps.note`；`resumeTask` 读取已持久化步骤，把已完成步的产出接回 sections、只续跑第一个未完成步起的余下部分，末步重新生成交付；runner 的 `resumeUnfinishedTasks` 改走 `resumeTask`（不再 reset 全清）。对应 Stage 1「持久化任务状态机」往深做的一步。
- **M32 自动清理策略**：`tasks.created_ts`（epoch ms）按龄——只删终态(done/failed)非归档、超 `ARK_CLEANUP_TASK_DAYS`(默认90天)的任务及交付文件，审计日志裁剪到 `ARK_CLEANUP_AUDIT_MAX`(默认5000)；`POST /api/maintenance/cleanup` 手动 + 调度器每 6h 自动，`ARK_CLEANUP_ENABLED` 可关。running/queue/归档一律不动。对应「自动清理」类运维治理能力。
- **M33 任务模板**：`task_templates` 表 CRUD + `POST /:id/run` 一键应用模板建任务（预填提示词/专家/技能/模型）；前端 `/app/templates` 页。把重复需求固化为可复用模板，提高建任务效率。对应「任务模板/最佳实践沉淀」类效率能力。
- **M34 任务另存为模板**：`POST /api/tasks/:id/template`——done 任务一键固化为模板（继承 prompt/expert/skills/model），TaskPage「另存为模板」按钮。与 M33 应用模板成对，形成「产出→沉淀→复用」闭环。
- **M35 模板字段真正生效**：应用模板时 `AgentOptions {expert?,skills?,modelHint?}` 贯穿 runner→orchestrator → planner/pipeline 与 router——expert/skills 落进任务记录，model 作 modelHint 偏好渠道路由（匹配渠道前置、非排他，挂了仍 failover）。模板配置从「只存」变「真用」。
- **M36 认证硬门禁**：写请求（POST/PUT/PATCH/DELETE→`/api/*`）需登录 401，读开放；`/api/auth/*` 自管；`ARK_REQUIRE_AUTH=0` 回退软门禁。对应 Stage 2「认证/多用户门禁」的点名落地（软→硬务实折中：只锁写、放开读）。
- **M37 定时任务可跑模板**：job `action` 支持 `template:<id>`，`runJob` 取模板 prompt + AgentOptions 跑任务；前端 Automation 加「跑模板」下拉。模板（沉淀）×字段生效（配置）×定时（调度）三合一。
- **M38 交付版本历史**：每次产出交付快照进隐藏 `_ark_versions/<name>/` + `file_versions` 表；`/api/versions` 列表 + 回滚；工作空间页「版本」面板。产物可回滚到任一历史版，零成本留档。
- **M39 Agent 角色可配置**：专家从「静态内置」→「内置 + 用户自建落库 CRUD（experts 表，多用户隔离）」；专家页「创建专属专家」可用（自建卡可编辑/删除，内置只读）。技能页加「新建 + 删除」（PUT upsert 新 .md、DELETE 删 .md，id 白名单防穿越）。对应 Stage 2「Agent 角色可配置」的点名落地。

## 演进原则（贯穿始终）

1. **可剥离**：本地单机（SQLite/SSE/自写状态机）与企业级（PG/Redis/队列）做成可平滑切换，不捆绑。
2. **类型共享**：前后端共享 TS 类型契约，接口演进有编译期校验。
3. **每个里程碑独立可验收**：像搭积木，每块做完能跑能看。
4. **数据不出本的底线**：默认只监听 127.0.0.1；任何接外功能（IM、联网）需显式开启并提示。
