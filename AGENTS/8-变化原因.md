# 8 · 变化原因（Agent 架构详解）

> 记录「为什么从 A 变成 B」。区分两种变化：**产品方向调整**（用户要求）与**工程实现调整**（我基于约束做的决策）。每一条都写「原来 / 现在 / 为什么」。

---

## 一、产品方向变化

### 变化 1：侧栏「提示词」入口 → 首页「场景库」（WorkBuddy 式）
- **原来**：侧栏有「提示词」项，对应 `/app/prompts` 平铺提示词列表。
- **现在**：侧栏**移除提示词项**；首页输入台上方做 **6 个场景胶囊**（文档处理/数据分析/…），点开下拉参考提示词，选中后输入台内出现**可移除场景标签** + 回填提示词正文；「全部场景」通向场景库页 `/app/prompts`。
- **为什么**（你的要求）：「舍弃提示词，改为像 WorkBuddy 一样**封装场景**，再根据场景提供对应参考提示词」。核心是从「给一串提示词」变成「让你选场景就能开工」，降低用户写提示词的负担。

### 变化 2：产品的技术阶段
- **原来**：纯前端 + mock 数据（任务步骤动画、假文件）。
- **现在**：接入真实后端（Fastify + SQLite），任务从首页提交 → 后端编排 → SSE 实时推 → 生成真实落盘文件。
- **为什么**（你要做全栈开发）：「我需要你做全栈开发」——把 mock 闭环换成真实后端闭环，打通端到端链路。

## 二、工程实现变化

### 变化 3：数据库 better-sqlite3 → Node 内置 node:sqlite
- **原来**：规划用 better-sqlite3（更快、API 顺手）。
- **现在**：`node:sqlite`（Node 22 内置 `DatabaseSync`）。
- **为什么**：Windows 缺 VS C++ 工具链，better-sqlite3 原生编译失败；内置 SQLite 零编译零依赖，接口几乎一致，符合「本地优先、免构建链」。详见踩坑日志 7-坑1。

### 变化 4：编排先自写状态机，不引 LangGraph
- **原来**：规划文档提到可用 LangGraph。
- **现在**：`orchestrator.ts` 手写步骤循环 + 事件广播。
- **为什么**：里程碑1 用预置计划即可验证链路；避免过早引重框架。预留 `plannerLLM` 接入点，之后无损替换。符合"按需演进"。

### 变化 5：API 创建接口从"等执行完返回"→"秒回 id + 后台异步 + SSE"
- **原来**（初版代码）：`await runTask(...)` 整个编排跑完才返回。
- **现在**：路由层生成 id 立即返回，`void runTask(id, prompt)` 后台跑，进度走 SSE。
- **为什么**：前端要能「秒开任务页 + 实时点亮」；重活异步化才能配合 SSE。详见踩坑日志 7-坑4。

### 变化 6：前端 API 地址用相对路径而非绝对地址
- **原来**：准备写 `http://127.0.0.1:4000`。
- **现在**：`BASE = import.meta.env.VITE_API_BASE ?? ""`（空串 → 相对 `/api/...`）。
- **为什么**：Vite `proxy /api → :4000`，开发零 CORS；生产可由 Fastify 托管静态 + 同源，避免写死端口。

### 变化 7：`steps.note` 列迁移
- **原来**：建表 `steps` 无 `note`。
- **现在**：建表加 `note`，并加「启动检测 column → ALTER 补列」迁移。
- **为什么**：老库已落盘，`IF NOT EXISTS` 不补列，直接 UPDATE 报错。见踩坑日志 7-坑2。

### 变化 8：规划器接入真实 LLM（LLM 优先 + 脚本降级双轨）
- **原来**：orchestrator 里硬编码 4 步预置计划（mock）。
- **现在**：`planner.ts` 先尝试已配置 LLM（openai 兼容 `/chat/completions`）拆 3~6 步 JSON；无渠道 / 失败即降级**场景化脚本计划器**（PPT/Excel/Word/调研关键词各自差异化步骤）。交付文件嵌入规划步骤，`task.model` 标记「LLM/内置计划器」。
- **为什么**：既保证「开箱可跑」（无 key 也能跑通闭环），又配 key 即自动进化成真 Agent 拆解；对前端透明。这是「mock 编排 → 真 Agent」的分水岭。模型渠道当前读环境变量（`ARK_CHANNELS`/`ARK_*`），数据库 CRUD 留待 M6。

### 变化 9：交付从 `.md` 占位 → 真实可编辑 Office 文件（PPT/Excel/Word）
- **原来**：orchestrator 最后一步只写一个 `.md` 占位文件（含需求与计划文本）。
- **现在**：新增 `tools/office.ts`，按需求关键词（ppt→pptxgenjs；excel→exceljs；默认→docx）生成**可编辑的真实 Office 文件**到 workspace，orchestrator 最后一步调用 `genOffice(prompt, plan, workDir)`。
- **为什么**：产品核心卖点是「一句话 → 交付**能直接打开可编辑**的真实文件」，`.md` 不满足。全 JS 库零原生编译（契合 Windows 免构建链），且生成的 Excel 含原生公式、PPT/Word 文字可编辑。

### 变化 10：模型路由（成功率选优）+ 交付验收/重试
- **原来**：planner 用 `getDefaultChannel()` 固定第一个渠道；交付文件生成后直接广播，不校验。
- **现在**：`models/router.ts` 按各渠道**成功率**选最优（统计写 SQLite `channel_stats`，planner 调用 `recordSuccess/Failure`）；`agent/verifier.ts` 对交付文件做**真实校验**（存在/非空/Office zip `PK` 头），不达标经 `verifyWithRetry` **限次重试（最多 3 次）**；新增 `GET /api/channels` 返回渠道+成功率。
- **为什么**：多模型接入后，坏渠道不能拖垮任务——router 自动降权；文件生成偶发失败不能直接交坏文件——verifier 自动重生成。这是「可靠性加固」的第一步，衔接 5-企业级演进路线 Stage 1（超时/熔断/重试）。

### 变化 11：工作空间从 mock 静态树 → 真目录扫描 + 与任务交付联动
- **原来**：前端 `Workspace.tsx` 用 `mock.ts` 的 `spaces/spaceFiles/appFiles` 静态展示。
- **现在**：后端新增 `GET /api/workspace`（`tools/workspace.ts` 真扫 `frontend/public/workspace/`，返回类型/大小/时间）；前端 Workweeks 页调 `listWorkspace()` 显示真实文件 + 下载 + 刷新 + 后端未启动提示。
- **为什么**：任务交付的文件与工作空间此前是「两套假数据」，无法闭环。真扫描后，**任务产出 → 工作空间可见 → 可在 Office 继续编辑/下载** 成为一套真实数据流，兑现产品「成果归你、可管理」的主张。

### 变化 12：对话从本地回显 → 真实 SSE 流式（LLM / 内置降级）
- **原来**：前端 `Chat.tsx` 用 `setTimeout` 500ms 后回显一句固定话，无后端。
- **现在**：后端 `POST /api/chat` SSE 逐 `token` 推送，最后 `done`。有模型渠道 → `chatStream` 真实模型流式；无 key/失败 → 内置回复**逐字流式**降级（依旧有流式体验）。前端 `sendChat` 逐 token 渲染，流结束把完整回复沉淀进 history 保持多轮上下文。
- **为什么**：对话是 C 端体验最直观的能力；流式是「打字机」效果的关键。真实模型与降级双轨与 planner 同思路——无 key 也能体验，配 key 即真。Ollama 也兼容该 SSE 协议，契合「数据不出本机」。

### 变化 13：技能从 mock 数组 → Markdown 落盘热加载；专家接 API
- **原来**：前端 `Skills.tsx` 用 `mock.ts` 的 `skills` 数组（只读，`code` 不可编辑）；专家卡也用 mock。
- **现在**：后端 `tools/skills.ts` 把每个技能存为 `skills/<id>.md`，元信息（name/desc/enabled）写在 HTML 注释 front-matter；`GET/PUT /api/skills` + `toggle` 读写落盘，**改完即生效、重启持久**。前端 Skills 页接真 API：列表 / 选中 / 代码可编辑 textarea / 保存 / 开关切换 + 未保存确认。专家 `GET /api/experts` + 前端接。
- **为什么**：技能是产品的「配方」，必须可被用户/Agent 编辑并热生效（这正是「Markdown 即技能」卖点）。落盘比数据库更直观——直接用编辑器改 `.md` 就是改技能；重启不丢是因为内容在磁盘。

### 变化 14：自动化从 mock 列表 → 本地 Cron 真调度
- **原来**：前端 `Automation.tsx` 用 `mock.ts` 的 `jobs/jobLogs` 静态数组，开关只是本地 state。
- **现在**：后端 `scheduler/jobs.ts`（jobs/job_logs 两张 SQLite 表 + CRUD + `startScheduler` 本地 30s 轮询），`routes/jobs.ts`（`GET/POST/PUT/DELETE /api/jobs` + `/:id/run` + `/logs`）。到点且启用的任务调 `runJob`→复用编排闭环 `runTask` 产出真实文件并记日志（同分钟防重）。前端 Automation 页接真 API：列表 / 开关 / 新建表单 / 手动执行 / 删除 / 最近执行。
- **为什么**：产品要「定时自动干活并交付」，用 minimalist 自研 Cron（每天 HH:MM / 每 N 分钟）而非引 heavy node-cron，够用且零依赖；自带防重避免同一分钟重复投递。将来要复杂表达式可平滑换 `node-cron`。

### 变化 15：模型渠道从环境变量 → DB 持久化 + CRUD / 设默认 / 验活
- **原来**：渠道读 `ARK_CHANNELS` / `ARK_*` 环境变量，改要重启、不可持久、无法在设置页管理。
- **现在**：`config/channels.ts` 改为读 SQLite `channels` 表（首启用内置 6 渠道 / env 引导种子）；`routes/channels.ts` 提供 `GET/POST/PUT/DELETE /api/channels` + `/:id/default`（设默认）+ `/:id/test`（验活，GET `{baseUrl}/models`）。router / planner 直接消费 DB 渠道，`channel_stats` 记录成功率。
- **为什么**：产品要「本地可管理、可持久」的模型配置。DB 存渠道让用户能在设置页**增删改、验活、设默认**而无需改环境变量重启；验活用零成本 `GET /models` 探活（无需真调模型）。风险点：`apiKey` 明文存本地 SQLite——符合「本地优先」但离生产有差距，标注为演进点（加解密/Vault，见 5-企业级演进路线）。

### 变化 16：连接器状态从 mock 全绿 → 真实探测/如实标记
- **原来**：前端 `Connectors.tsx` 用 mock，全部显示"已连接/已开启"（假在线）。
- **现在**：后端 `GET /api/connectors` 返回真实状态——模型渠道（读 DB 报「N 个渠道·默认 X」）、Ollama 本地（`probeOllama` 实测 `GET localhost:11434/api/tags`，未启动如实报未连接）、联网搜索/内置浏览器/IM 桥（尚未接入，如实标「未接入」而非假在线）。前端接 API + 刷新。
- **为什么**：连接器页的意义就是「告诉用户当前到底能用什么」。假"已连接"会误导。真探测（尤其本地 Ollama）离线可演示，且与产品「数据不出本机、自主可控」主张一致。

### 变化 17：任务配置显示真实模型名（渠道→LLM 拆解打通可视）
- **原来**：`task.model` 只标「LLM / 内置计划器」。
- **现在**：planner 的 `llmPlan` 拿到 `pickChannel()` 所选渠道后，成功时返回 `{ name } · { model }`；orchestrator 用 `model` 填充 `task.model`。配了 key 走真 LLM 时任务配置显示如「DeepSeek · deepseek-chat」，无 key 降级显示「内置计划器」。
- **为什么**：让「渠道管理 ↔ 真实 LLM 拆解」这条链路在任务页可见可验证——用户在设置页配了哪个渠道，任务页就如实显示用了哪个模型，闭环透明。

### 变化 18：场景库从 mock → 后端 GET /api/scenarios
- **原来**：Home 与 Prompts 都 `import { scenarios } from mock.ts`。
- **现在**：后端 `data/scenarios.ts` + `routes/scenarios.ts` 提供 `GET /api/scenarios`；前端加 `listScenarios`，Home/Prompts 均从 API 拉取（mock 仅作离线降级，页面不断）。
- **为什么**：场景是产品内容（同技能/专家），由后端统一提供后，首页场景胶囊与提示词库页一起解耦 mock，且将来可编辑/持久化。

### 变化 19：侧栏「最近任务」从 mock → 真实任务列表
- **原来**：Sidebar 用 `mock.ts` 的 `recentTasks` 静态列。
- **现在**：后端加 `GET /api/tasks` 列表摘要（`store.listTasks` 从 SQLite 按 created 倒序）；前端 `listTasks()`，Sidebar 改从 API 拉真实任务（mock 仅离线降级）。
- **为什么**：侧栏「最近任务」反映真实使用痕迹（含定时任务自动化产出），比静态示例更真实；与任务闭环打通。

> 注：变化 20~27 与 `docs/agent-architecture/8` 的 M20~M27 对应（两套编号体系不同：docs 是「M 里程碑」，AGENTS 是「变化 N」）。以下按 AGENTS/0 的总览同步记录。

### 变化 20：工作空间全文搜索（FTS5 trigram）——中文文件名也能搜
- **原来**：资料库只能按空间浏览，Cmd+K 只搜任务标题。
- **现在**：`tools/searchIndex.ts` 用 SQLite FTS5 **trigram** tokenizer 建文件名索引；`GET /api/workspace/search` 子串匹配；资料库搜索框 + Sidebar Cmd+K「工作空间文件」区。
- **为什么**：`unicode61` 按词切分对中文无效，trigram 做真正的 3 字符子串匹配（搜「战略分析」命中「市场战略分析PPT」）；刻意只索引文件名（用户记忆入口），不读文件内容避免大文件/隐私。

### 变化 21：全局任务事件 + 浏览器通知 + 侧栏自动刷新
- **原来**：侧栏「最近任务」只在首次挂载拉一次（陈旧 bug），任务后台跑完无任何通知。
- **现在**：后端 `GET /api/events` 全局 SSE（publish 对 subscribeAll 扇出）；前端 `subscribeGlobal`，任意页弹浏览器通知（完成/失败），侧栏 done/error 自动刷新。
- **为什么**：一条不受页面限制的任务事件总线，补齐「异步任务完成通知」与「列表自动新鲜」两个体验缺陷。

### 变化 22：任务历史归档
- **原来**：终态任务（done/failed）与所有历史平铺在一个列表，越积越乱。
- **现在**：`tasks` 表加 `archived` 列；`POST /:id/archive` 归档/取消归档（运行中 409）；侧栏「查看归档」切换 + 右键菜单；TaskPage 终态任务加按钮。
- **为什么**：让终态任务一键收起进归档区、平时最近任务只显示活跃项，降低列表噪音（且已归档不清真删、可取消）。

### 变化 23：给历史对话补全文搜索
- **原来**：M19 对话已持久化，但历史对话本身不能搜（"上次聊的方案在哪"只能翻会话栏）。
- **现在**：`chat_messages` 建 FTS5 trigram 索引（appendChatMessage 增量入索引 + 启动 reindexChats 重建）；`GET /api/chat/search` 按会话去重、多用户隔离；Sidebar Cmd+K 加「历史对话」区，点命中跳 `/app/chat?sess=`。
- **为什么**：把 Cmd+K 一处搜索从「任务+文件」扩展到「任务+文件+对话」，让三个隐形资产都可达。

### 变化 24：进程重启任务恢复
- **原来**：任务执行只靠内存串行队列（runner.ts 的 `tail`），后端崩/重启后 queue/running 任务**永久孤儿**。
- **现在**：`getUnfinishedTasks()`（读非归档 queue/running 遗留任务含 user_id）+ `resumeUnfinishedTasks()`（启动时重新入队，`resetTask` 幂等重跑，打印「恢复 N 个遗留任务」）。
- **为什么**：本地单机重启不罕见（改码/关窗/崩溃），不给遗留任务兜底它们就"丢了"；从头重跑最稳（逐步断点续跑需额外落 last-completed-step，后置）。

### 变化 25：自动化测试（vitest）
- **原来**：全仓库**零自动化测试**，全靠手动 curl E2E。
- **现在**：vitest 套件（`ARK_DB_PATH`/`ARK_TEST` 隔离临时库，绝不碰 data/ark.db）——store/events/runner(串行+失败兜底+恢复)/HTTP(Fastify inject) 26→31 用例；`npm test`/`typecheck(tsconfig.test.json)`/`build` 三件套。
- **为什么**：每改一个里程碑都在赌前面没坏；测试一上马立刻揪出 2 个真实 bug——`insertTask` INSERT 缺 `archived` 列、`getUnfinishedTasks` 选 `user_id` 忘 `AS userId`（M24 恢复会静默丢登录用户任务的归属）。

### 变化 26：结构化日志（pino + taskId 贯穿）
- **原来**：只有 Fastify 默认请求日志，任务执行管线不发任何业务日志。
- **现在**：`util/log.ts` 统一 pino（`service:"ark-backend"` 常驻 + `taskLogger(id)` 用任务 ID 作贯穿键）；orchestrator 打 started(plan/model/userId)/deliverable/finished，runner 打 executionStarted/failed。
- **为什么**：任务是异步入队执行、无请求对象，用任务 ID 作贯穿键最自然；HTTP 请求带 Fastify 自动 reqId —— 出问题可按 taskId/reqId 串联全链路。

### 变化 27：多渠道熔断器
- **原来**：M14 failover 只"失败就换渠道"，但持续故障的渠道仍每次被从头试到尾、每次空耗 20s 超时。
- **现在**：路由每渠道**内存熔断**——连续失败 5 次 open 短路该渠道，10s 冷却后转 half-open 放一次探测（成功复位/失败重置冷却）；`pickChannel`/`orderedChannels` 跳过被熔断渠道。
- **为什么**：熔断与 retry/failover 正交（retry 管临时抖动→失败兜底；failover 管单点失败；熔断管**持续故障**），避免反复重试已知坏源。

### 变化 28：验收回归评测集——把核心卖点固化为回归断言
- **原来**：自动化测试（M25）覆盖了 store/events/runner/router/HTTP，但**没有覆盖"真实 Office 交付生成"这条验收路径**（http.test 刻意不建真实任务避免写盘/慢）。
- **现在**：新增 `test/acceptance.test.ts`（12 用例，~0.5s）——把「一句话→消费可编辑 Office 文件」核心卖点固化为回归断言：① 历史成功任务的 prompt → `detectKind` 正确类型映射（6 组）；② PPT/Excel/Word 真实生成、合法 zip、Excel 用 ExcelJS **读回内容**验证可编辑可读；③ verifier 重试对始终失败的生成按 maxTimes 重试后抛错；④ `defaultTool` 内容整编产出非空。
- **为什么**：虽然不是完整跑任务（那慢 + 需 LLM），但交付生成是每类任务的必经终点；把它的验收标准固化成断言，任何改动让某类 Office 生成退化都会立刻变红——与 stats 主线：先有测试（M25）再固化历史成功场景（M28）。
- **演进衔接**：这是 [5-企业级演进路线](5-企业级演进路线.md) Stage 1「验收回归评测集：把历史成功任务固化为评测集，防回归」的点名落地。

### 变化 29：操作审计日志（onResponse 钩子全局落审计）
- **原来**：后端对**所有写请求**（建任务/登录/改渠道/删空间/发消息…）**零留痕**——一旦误操作或账号被滥用，无从追溯「谁在什么时候做了什么」。
- **现在**：`store` 加 `audit_log` 表；新增 `routes/audit.ts`，在**根上下文**装一个 `onResponse` 钩子，把每个 POST/PUT/DELETE 到 `/api/*` 的请求用 `currentUser` 归到人（未登录记匿名），method+url → 可读中文动作（创建任务/登录/删除渠道…）+ 目标 id，写进 `audit_log`；`GET /api/audit` 可查（倒序、可 limit）。
- **为什么**：审计要 **一处实现、覆盖所有端点（含未来新增）**，用钩子在根上下文统一接入、零侵入各路由（避免逐路由加一遍）。刻意不审 GET（读操作无副作用、噪音大）；写请求**无论成败都记**（比如字段校验失败的 POST 也留痕），构成防抵赖的完整痕迹。
- **工程坑（7-踩坑12）**：Fastify 的 `onResponse` 是**封装的**——装在带 `prefix` 的插件里只会审计「该插件自己的路由」。审计钩子若和 `GET /api/audit` 放同一插件，其余端点全部漏记。必须**在根上下文**装钩子、视图端点另放前缀插件。
