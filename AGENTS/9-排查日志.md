## 排查 1：任务页交付文件 checks 全 ○，但 SSE 明明广播了✓

### 症状
- 后端 `GET /api/tasks/:id` 返回 `status: done`、步骤全 `done`、交付 `.md` 文件存在，但 `checks: [false,false,false]`。

### 排查过程
1. **先看事件流**：抓 SSE，确认 `check` 事件被反复广播（12 次），且最后一个 `check` 载荷里 checks 是 `[true,true,true]`。→ 说明**运行时内存里 checks 是对的**。
2. **看接口返回**：`GET /api/tasks/:id` 却返回全 false。→ 接口从**库**读，库里是 false。
3. **直接查库**：用 `node:sqlite` 读 `tasks` 表的 `checks` 字段，确认库里就是 false。
4. **对比定位**：SSE（读内存 `task.checks`）✓ vs 接口（读库 checks）○ → 差异在「内存 vs 持久化」。
5. **读代码**：`orchestrator` 只在循环里改 `task.checks` 并 publish，**结束前没把 checks 写回库**；`getTask` 读库自然是旧值。

### 结论
内存态与持久态不一致：广播给实时的那条线更新了，落库给快照/刷新的那条线漏了。补 `updateTaskChecksAndTimeline` 落库即修复。

## 排查 2：浏览器连 5173 报 ERR_CONNECTION_REFUSED

### 症状
GUI 测试导航 `http://127.0.0.1:5173/app` 时 `ERR_CONNECTION_REFUSED (-102)`，页面打不开。

### 排查过程
1. **curl 探测**：`curl 127.0.0.1:5173` → `frontend:000`（不通）；`curl 127.0.0.1:4000` → `backend:200`（后端好）。
2. **看前端日志**：`tail /tmp/ark-frontend.log` → 发现 Vite 日志写的是 `Local: http://localhost:5174/`。→ **它根本不在 5173！**
3. **推断原因**：早前 `--port 5173` 时 5173 被残留进程占用，Vite 默认换到 5174；后续浏览器一直连 5173 自然拒绝。
4. **清理+锁端口**：`pkill -f vite`，用 `--port 5173 --strictPort` 重启，`curl` 确认 `frontend:200`。

### 结论
`--port` 不带 `--strictPort` 会静默换端口。排查连不上服务时，第一件事看服务日志的 `Local:` 真实端口，别假设。

## 排查 3：前端订阅 SSE 收不到事件？ / GUI 注入 React 受控组件不生效

### 症状（GUI 测试部分）
工作台首页 UI 渲染完全正常（侧栏 + 6 场景胶囊 + 输入台 + foot 全在），但：
- `Playwright.fill` 设了 DOM value，React 受控 state 不同步 → 提交时 `v` 为空，不发起请求；
- `dom_cua.click` 点击场景胶囊后下拉菜单未展开（看似 onClick 没触发）；
- 个别 locator（`getByRole("发送")`）定位到 count=1 但 click 超时。

### 排查过程
1. **先排除业务**：用 curl 直接打后端 API，`POST/GET/SSE` 全通，任务正常做完、文件落盘、checks 全绿 → 后端业务没问题。
2. **排除数据库**：查库正常。
3. **观察行为特征**：fill 后 DOM value 变化但 React 受控组件（`onChange→setState`）不触发——这是「注入 vs 真实输入」的典型差异：真实键盘输入会走 keydown→input→change 事件链，而 `fill` 直接设 DOM value 不派发完整事件链。
4. **对比**：`type`（Playwright 逐字符）在个别轮次写入成功，但后续提交仍不稳定——IAB 注入对 React 受控组件/中文文本的可靠性有限。
5. **结论**：这是**测试工具（IAB）注入的固有限制**，不是应用 bug；应用 `onChange→state→submit` 是标准 React 模式，真实用户键盘必然触发。

### 结论
- 后续 GUI 自动化：优先用能触发完整事件链的方式（真实键击），或直接走 API 层做 E2E 断言；对 React 受控组件避免 `fill`。
- 本轮业务正确性以**API 层 E2E** 为准（已全绿）；交互部分受工具限制如实记录。

## 排查 4：`tsc` 用 npx 拉错包
### 症状
`npx tsc` 报"这不是你要找的 tsc"并尝试安装 `tsc@2.0.4`（废弃包）。
### 排查
本机没全局 typescript，`npx` 去 npm 找 `tsc`（历史占位包）。应调用项目本地 `node_modules/.bin/tsc`。
### 结论
用 `./node_modules/.bin/tsc -p tsconfig.json --noEmit`（或 `npm run typecheck`），别用裸 `npx tsc`。

## 排查方法总结（沉淀）

1. **先分层**：问题在「前端 UI / 前端逻辑 / 网络 / 后端 API / 数据层」哪一层？用 curl 把后端隔离出来单测。
2. **SSE 抓流**：`curl -N .../events` 看实际广播的事件与载荷，判断是「广播错」还是「读取错」。
3. **内存 vs 持久化**：当「实时推送对、快照错」，八成是广播线更新了、落库线漏了。
4. **服务连不上先看日志端口**：别假设端口号。
5. **GUI 注入受限时**：明确「工具限制 vs 应用 bug」，用 API 层做权威 E2E 断言兜底。
