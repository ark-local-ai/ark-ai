# 2 · 面试准备指南（Agent 架构详解）

> 面向：用这份项目"讲清楚自己做了什么 + 为什么这样设计" 的面试准备。聚焦**技术决策背后的权衡**，面试官最爱问这类问题。

---

## 一、一句话电梯介绍

"我做了一个本地优先的 AI Agent 生产力工作台：用户一句话描述需求，系统拆成步骤、逐个执行、最终交付可编辑的真实文件（PPT/Word/Excel）。全栈用 TypeScript，前端 React，后端 Fastify + Node 内置 SQLite，任务进度用 SSE 实时推给前端，数据默认不出本机。"

---

## 二、高频面试问答（含加分点）

### Q1: 为什么后端选 Fastify 而不是 Express / NestJS？
- Express 异步支持弱、无内置 schema 校验，性能约是 Fastify 的 1/2~1/3。
- NestJS 重（DI、装饰器、模块系统），本地工具型产品不需要这么重。
- Fastify：性能好、插件化、自带 JSON schema 校验，和 TS 契合。**加分**：它的事件循环是异步友好的，很适合 SSE 长连接。

### Q2: 为什么用 Node 内置 node:sqlite 而不是 better-sqlite3 或 Prisma？
- better-sqlite3 更快但**需要原生编译**（Windows 要 VS C++ 工具链），我的环境装不上，会阻塞 CI/跨平台。
- Prisma/Mongoose 对简单本地库过重。
- Node 22 内置 `node:sqlite`：**零依赖、零编译、同步 API 简单**。**加分**：这是"本地优先、数据不出机"产品的合适底座，还避免供应链依赖。

### Q3: 任务进度为什么用 SSE 而不是 WebSocket？
- 任务执行是**服务器单向、持续推送**给浏览器的场景，SSE 正好匹配：服务器→客户端单向 JSON。
- WebSocket 是双向全双工，本例前端几乎不反向发数据，用它是过度设计。
- SSE 基于 HTTP，天然过代理（Vite proxy）、自动重连、事件类型命名（`event: step`）。
- **加分**：我做了 `replay` 缓存，迟订阅的 SSE 连接也能立即拿到已发生的事件，不丢进度。

### Q4: 编排层为什么先自写状态机而不是 LangGraph？
- 里程碑1 目标是把「创建→执行→交付」链路跑通，用预置计划演示即可。
- 引 LangGraph/重框架会带来学习成本与依赖，与「本地优先、轻量」目标冲突。
- 我在 orchestrator 里留了 `plannerLLM(prompt) => Step[]` 的接入点，之后无损替换。
- **加分**：说明我懂得"按需演进"，不为炫技提前引入复杂度。

### Q5: 数据一致性怎么保证的？
- 任务/步骤/产物写 SQLite（事务级别由单文件库天然保证）。
- 每一步状态变更：先落库（`updateStepStatus`），再广播 SSE（`publish`），查询快照 `GET /api/tasks/:id` 从库读，保证「接口看到的」和「实时推送的」一致。
- **加分**：指出最终状态（checks/timeline）也写回库，前端刷新后仍能恢复到完整状态。

### Q6: 前后端怎么连的？
- Vite dev server `proxy /api → http://127.0.0.1:4000`，前端用相对路径 `/api/...`，开发零 CORS 烦恼。
- 生产可让 Fastify 托管前端 dist 或由反代合并。

### Q7: 前端场景库（WorkBuddy 式）怎么设计的？
- 首页输入台上方一排**场景胶囊**（文档处理/数据分析/…），点开下拉该场景的**参考提示词**，选中后输入台内出现**可移除标签**（场景名 ×）+ 回填提示词正文。
- 设计动机：把「用户不擅长写的提示词」封装成「选场景就能开工」，降低使用门槛。
- `scenarios` 数据在 `mock.ts`，类型化（`Scenario`/`ScenePrompt`），后续可接后端 CRUD。

## 三、可能被追问的深挖点

1. **Node:sqlite 是实验特性**（Node 22 会打 ExperimentalWarning）——你怎么看待稳定版本依赖？答：功能已够用，标记为可选替换点，未来可无痛切 better-sqlite3（接口几乎一致）。
2. **并发/多任务**：目前事件总线是内存 Map。企业级可换 Redis pub/sub 或消息队列——这正好衔接 5-企业级演进路线。
3. **SSE 断线重连**：EventSource 自动重连，后端 replay 缓存；但若是进程重启，内存缓存丢失，需从 DB 重建——记录为待改进点。
4. **安全**：成果下载做了目录穿越防护（normalize + startsWith 校验），本地服务只监听 127.0.0.1。

---

## 四、项目里的硬技能清单

- **TypeScript**：严格模式、类型共享（前后端共用 Task/Step/Artifact 定义）
- **Node.js**：内置 SQLite、流式文件、ESM、进程管理
- **Fastify**：路由、schema、SSE、CORS、静态服务
- **React 19**：受控组件、路由 state、hooks、EventSource 订阅
- **SSE / 事件驱动**：事件总线、replay、心跳
- **工程化**：monorepo 多包、Vite proxy、tsc 严格校验、SQLite 迁移

---

## 五、一句话收尾

"这套架构的取舍都围绕同一个目标：**本地优先、轻量、数据不出本机**。能用 Node 内置能力就不引依赖，能用 SSE 就不上 WebSocket，能自写状态机就先别上重框架——每一步都留了往企业级平滑演进的口子。"
