# 7 · 踩坑日志（Agent 架构详解）

> 记录真实踩过的坑：现象 → 原因 → 解决 → 教训。按时间倒序。

---

## 坑 1：better-sqlite3 原生编译失败（Windows 缺 VS C++ 工具链）

- **现象**：`npm install` 在 `better-sqlite3` 处报错 `gyp ERR! find VS You need to install the latest version of Visual Studio ... Desktop development with C++`，安装失败。
- **原因**：better-sqlite3 是 C++ 原生模块，安装时要 node-gyp 编译；本机没有装 VS Build Tools C++ 工作负载。
- **解决**：**换掉 better-sqlite3**，改用 **Node 22 内置的 `node:sqlite`（DatabaseSync）**——零依赖、零编译、同步 API 几乎一样（`prepare().run/get/all`）。改 `db/store.ts` 即可，接口基本平移。
- **教训**：
  1. 在 Windows / 无编译链环境，优先考虑**纯 JS / 内置**模块，避免原生依赖。
  2. "本地优先、轻量"的产品尤其要省去构建链——内置 SQLite 是绝佳选择。
  3. 选库前先确认目标平台能否编译（Windows/Linux/Mac 原生模块差异大）。

## 坑 2：`CREATE TABLE IF NOT EXISTS` 不会给旧表补列

- **现象**：任务执行时 `UPDATE steps SET note=?` 报 `Error: no such column: note`。
- **原因**：第一次建表 `steps` 漏了 `note` 列；库已落盘后，`IF NOT EXISTS` 不会加列。
- **解决**：
  1. 修正建表 SQL 补上 `note TEXT`。
  2. 加**迁移逻辑**：启动时 `PRAGMA table_info(steps)` 检查，没有 `note` 就 `ALTER TABLE steps ADD COLUMN note`。
- **教训**：Schema 演进不能只靠 `CREATE IF NOT EXISTS`；要么统一迁移框架，要么至少做幂等的「检测列→补列」。

## 坑 3：`npm run dev -- --port 5173` 被占用时悄悄换端口

- **现象**：浏览器连 `127.0.0.1:5173` 反复 `ERR_CONNECTION_REFUSED`，但 Vite 日志显示它在 **5174** 起服务。
- **原因**：5173 端口被早前残留实例占用，Vite 默认「换端口继续」而非报错，导致我以为的地址根本没人监听。
- **解决**：用 `--strictPort` 强制占用了就报错，并 `pkill -f vite` 清残留，再明确 `--port 5173 --strictPort` 重启。
- **教训**：`--port` 不带 `--strictPort` 会静默换端口，排查链接不上时先看 `Local:` 那行真实端口；脚本里可固定端口防漂移。

## 坑 4（记录）：后端「占位 id」阻塞了 SSE

- **现象**：最初 POST 里我 `await runTask(prompt)` 等整个编排跑完才返回 id，导致前端要很久才拿到 id、SSE 的意义被抹掉。
- **原因**：把「创建」和「执行」耦合在同一个 await 里。
- **解决**：`randomUUID` 在路由层先生成 id 立即返回，编排 `void runTask(id, prompt)` 异步后台跑，进度走 SSE。
- **教训**：SSE/流式系统的「创建」接口应秒回 id，重活异步化。

## 坑 5（记录）：`updateTaskStatus` 最终 checks 没写库

- **现象**：任务状态 `done`、SSE 里 checks 都打勾了，但 `GET /api/tasks/:id` 快照查出来 checks 是 ○○○。
- **原因**：checks 只在内存 `task.checks` 里更新并广播，结束时没把最终 checks 写回 tasks 表，快照从库读就是旧值。
- **解决**：结束前调用 `updateTaskChecksAndTimeline(id, task.checks, task.timeline)` 落库。
- **教训**：内存态和持久态要保持一致——「广播给实时」和「落库给快照/刷新」是两条线，都要写。

## 坑 6（M14/M17+）：`node dist/server.js` 起后端报 `ERR_MODULE_NOT_FOUND`

- **现象**：构建后 `node dist/server.js` 起服务报 `ERR_MODULE_NOT_FOUND`，找不到模块。
- **原因**：后端源码 import **省略 `.js` 扩展名**（`./routes/tasks` 而非 `./routes/tasks.js`），这在 `tsx`（esbuild）下能解析，但纯 Node ESM 跑编译后的 `dist/` 就找不到文件。
- **解决**：开发/验证一律用 **`npx tsx src/server.ts`** 起后端，不要用 `node dist/server.js`。
- **教训**：TS ESM + `moduleResolution:bundler` 省略扩展名的写法，仅在 tsx 下成立；直接跑 node 需补 `.js`。

## 坑 7（M21~M27）：Windows 上 `:4000` 残留旧 node 进程 → 新代码间歇 400

- **现象**：改完后端重启后，新路由有时 200 有时 400，行为不一致。
- **原因**：Windows 的 `SO_REUSEADDR` 允许多个 node 进程同端口；改了代码只 kill 主 PID，旧的还在抢端口，返回旧代码的结果。
- **解决**：`netstat -ano | grep :4000` 找到**所有** LISTENING PID，逐个 `taskkill //F //PID` 清干净再重启。
- **教训**：重启后端前先确认端口上只有一个新进程；`pkill -f` 在 Windows 上常杀不干净。

## 坑 8（M23/M25）：node:sqlite `.all(...数组)` 过不了 TS 重载

- **现象**：`db.prepare(sql).all([a,b])` 传数组作为单参数时 tsc 报重载错误。
- **原因**：`node:sqlite` 的 `.all()` 类型签名是变参 `(...params)`，传单参数组不被任一重载接受。
- **解决**：按分支直接展开/显式传参数，不要整体传一个数组（如 `userId ? .all(q, userId) : .all(q)`）。
- **教训**：node:sqlite 的 `.all/.run/.get` 参数是变参而非数组；TS 下尤其容易踩。

## 坑 9（M26）：Fastify 5 `logger` 只接受配置对象、不接受 pino 实例

- **现象**：`Fastify({ logger: <pino实例> })` 抛 `fastify error: logger options only accepts a configuration object`。
- **原因**：Fastify 5 变更——`logger` 选项只接受布尔或**配置对象**，**不再接受 pino 实例**（v4 可以传实例）。
- **解决**：`util/log.ts` 导出 **pino LoggerOptions 配置对象**给 Fastify 用；任务执行层再用 `pino(loggerOptions)` 单独建实例（共享同一配置）。
- **教训**：升级 Fastify 要看 logger 选项语义变化；结构化日志的「HTTP 与任务共用配置」应导配置而非实例。

## 坑 10（M27）：残留 `dist/` 遮蔽 `src/` 模块，测试读到旧导出

- **现象**：跑 vitest 全量时 `router.isChannelOpen is not a function`（单文件跑却正常）。
- **原因**：仓库里残留的 build 产物 `dist/models/router.js` 是**旧版**（无 isChannelOpen），vitest 在某些 worker 里解析到了 dist 而非 src。
- **解决**：跑测试前删掉 `dist/`（gitignore、安全）；也顺带清理 vitest.config 里已废弃的 `poolOptions`（Vitest 4 起改 top-level）。
- **教训**：源码旁别留陈旧 build 产物；测试被"遮蔽"时先怀疑有没有旧的同路径文件。

## 坑 11（M25）：测试一上马就揪出 2 个潜伏 bug

- **现象**：`getUnfinishedTasks` 返回的 `userId` 恒为 undefined（M24 重启恢复丢用户归属）；`insertTask` 写入的 `archived` 恒为 0（直接插入丢归档标记）。
- **原因**：① 该函数 SQL `SELECT user_id` 却忘 `AS userId` 映射，返回对象里字段名是 `user_id` 而代码读 `.userId`；② INSERT 语句缺 `archived` 列。
- **解决**：① SQL 补 `AS userId`；② INSERT 补 `archived` 列持久化。
- **教训**：两个都是"没测看不出来、一写测试立刻现形"的典型——再次印证自动化测试的价值（M25 的核心产出不只是测试，还有抓出的真 bug）。

## 坑 12（M29）：Fastify `onResponse` 钩子是封装的——装错层级直接漏审

- **现象**：把「全局写请求审计钩子」和 `GET /api/audit` 一起放在 `routes/audit.ts`（以 `prefix: "/api/audit"` 注册），HTTP 测试发现**除审计端点外其余所有写请求都没落库**。
- **原因**：Fastify 的 `addHook` 是**插件封装**（encapsulation）的——`onResponse` 只对「注册它的上下文内」的路由生效。装进带 `prefix` 的审计插件里，只审计了该插件自己的路由（也就是 GET 查看器，还被跳过），其他 `/api/auth`、`/api/tasks` 等一律不触发。
- **解决**：把钩子拆成 `installAuditHook(app)`，在 **server 根上下文**（`Fastify()` 之后、所有路由注册之前）按装；`GET /api/audit` 视图端点另放前缀插件。E2E 印证：register/login/建删除渠道全部落审计并正确归到当前用户。
- **教训**：凡是"一处接入、覆盖全应用端点"的钩子（审计、指标、公共中间件），必须确认挂在**根上下文**；放子插件是静默漏掉的经典陷阱。单测因封装边界会立刻变红，聊胜于手动排查。

## 坑 13（M31）：断点产出的 note 若写在 running 态会被 done 清空——断点内容丢了

- **现象**：逐步断点续跑（M31）想给每步持久化产出供重启接回。一开始在 `updateStepStatus(sid, "running", note)` 里写 note，结果重启时续跑读不到任何已完成步骤的产出。
- **原因**：`updateStepStatus` 的 SQL 是 `UPDATE steps SET status=?, note=?`——随后把步置 done 时调用的是 `updateStepStatus(sid, "done")`（没传 note），SQL 把 `note` 重置回 `NULL`，先前写的断点内容被清掉。
- **解决**：把产出整篇（JSON.stringify(stepContent)）放在**置 done 的调用**里：`updateStepStatus(sid, "done", JSON.stringify(stepContent))`——status=done 之后不会再被覆盖，note 稳定保留，`resumeTask` 的 `sectionFromNote` 才能接回。
- **教训**：任何"状态转变时会写一次、之后不再写"的持久化字段，要写在**终态那次调用**里，不能写在过渡态。写完跑一遍"中断→重启→检查续跑点"的恢复路径验证，别只测 happy path。
